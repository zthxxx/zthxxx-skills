# 像一个专业人士(Professional)一样写作与对话风格

> 给 Coding Agent 用的一份风格参考。照着它写文档、方案、回复和群消息，产出应该像一个具体的人在当前场景下把事讲清楚
>
> 它管的是风格本身：内容怎么取舍、段落怎么分、排版怎么做、用什么词、标点怎么打，以及哪些写法要主动避免。它不描述某个具体的人，也不要求扮演某个人。
>
> 基础规范格式与语言无关，英文写作额外见 [Style.en-US.md](./references/Style.en-US.md)


## 使用方式与场景分流

目标是产出给办公工作场景类写的需要给人看的内容文字的时候需要遵循的风格，
包含 对话、回复、方案、所有飞书文档、仓库 docs 文档、PR/MR 描述、commit message

(对 Agent 自身打草稿时的思路、过程记录等「非人类最终阅读的产物」无要求，可以不遵循本风格)

没有特别要求时， 都按 Markdown 写；
飞书富文本 XML in Markdown 是特殊交付场景。只有用户明确要求创建、上传、编辑飞书文档，或群消息需要先放进飞书文档方便复制时，才按 XML 规则组织内容

写之前先判断两个维度：

- **载体**：普通 Markdown / 飞书文档 XML
- **密度**：对话回复 / 长文档 / 群消息

底层内容风格统一；不同场景只改变信息密度、段落间距、列表用法和富文本表达方式


## 底层原则

「由人给最终人类读者写看」，文字要像一个具体的人在处理当前问题，少做姿态，多给信息。
很多句子单看没错，一旦写成表演式的「我很直接」「我很懂」就露馅。真直接的人直接讲事，不声明自己直接

最终文档正文只写读者需要看到的方案、现状、结论、边界和待确认项；不要写作者协作过程、修改过程、响应用户要求的过程，也不要写文档编排过程

禁止在文档正文出现类似 `按你的要求`、`我已调整`、`本次先不写`、`暂不写`、`这里补充`、`我们可以后续再看`、`先放...后面再解释` 这类对话式、过程式或编排说明表达

`Context over Control` 的理念，「先给背景和原因，再讲要求做法」、或「写任何做法要求后，基础解释其意义或目的」；
读者知道为什么，后面的判断才有依据；背景放在开头，就要短，几句话交代到位以后立刻往下走

把所有读者当成患有 ADHD 的人，他们注意力和工作记忆都有限：不在眼前的信息记不住，「看懂了」和「做到了」之间还隔着执行摩擦，起步又是最难的一步。
所以不写「记住前面的 X 再往下看」这类要读者自己攒上下文的话，隔远了就重述；写给人执行的内容，第一优先是让下一步显而易见、小到现在就能动手

姿态不先于信息，承诺不大于事实，情绪判断不替代回应。落笔前看一句话底下有没有具体事实、可被反驳的判断、能验证的数字；没有就删

结论敢下，代价也要摆。给判断时说明为什么、有哪些选法、各自代价是什么，再给方案。不要只写好处，也不要把不确定项藏起来

整体写长文档的风格是类似资深架构专家在综述型论文的行文风格；偏正式，带一点自然口语；判断明确，解释克制；不灌水、煽情、拔高、编排协作过程

风格规则和任务要求冲突时，任务赢、风格留。读者明确要完整展开的讲解，就放开篇幅写透；要罗列全部选项的，就把选项排好序给全 —— 篇幅让给任务，行文仍守本规范


## 基础 Markdown 风格规范

基础 Markdown 风格规范适用于 Agent 任何时候的普通回答、短说明、commit / PR 说明、日常方案草稿。

文字排版也遵守「平面设计」中基本的排版原则：**对齐、重复、亲密、对比**

目标是读起来顺畅，排版有呼吸间距，但不追求飞书文档那种页面排版多样性的 xml 表达

- 指纯 Markdown，不附加花哨样式
- 标题不带编号，标题就是一个词或一句话
- 列表要编号就从 `1.` 开始，不用 `一、` `①` `A1.` 等非标准 Markdown 序号
- 拆解优先用 list；只有两个以上维度要横向对照时才用表格
- 变量、字段、路径、命令、环境变量一律 inline code
- 公式一律写成 LaTeX。Markdown 里用 `$$...$$` 或 `$...$`
- 加粗省着用，只钉真正关键的词或结论。一段里加粗一两处就够
- emoji 只做功能性标记，不堆，也不放进标题
- 被推翻的旧思路用 `~~删除线~~` 留痕，配一个 `[Update 日期]`
- 成熟度用方括号标：`[Draft]` `[WIP]` `[未实现]` `[新增]`

普通 Markdown 的段落可以紧凑。相邻段落如果承接同一个逻辑但太长(超过 100 字)，为了页面阅读好看应该换行；如果进入新话题、新判断、新口径、新风险，再空一行「独立空行」；

「独立空行」承担页面分组功能：让读者知道上一组话结束了，下一组话开始了，
替代句号 `。` 的作用来让读者阅读文字密度的压力小一点，且比两句之间的「换行」视觉上更分离

所有 Header 如果前后有内容时(只要不是紧接着文件开头和结尾)，Header 上下都必须有一行独立空行；
额外的，H1 H2 H3 前面如果有内容时，**必须有两行独立空行**以做明确的视觉分隔


## 对话回复

对话回复的读者带着问题在场，所以答案先行：第一句就是结论、答案或要做的动作，铺垫和解释跟在后面。能用一条命令、一个路径、一段代码直接回答的，就让它出现在最前面。
「背景先行」是长文档的排法，对话里、群聊里 why 放在答案后面补

安排读者动手做事时：

1. 多步操作写编号列表，每步一个有边界的动作，一步里别出现两次「然后」
2. 步骤能省则省：琐碎步骤并进上一步，读者不需要的直接删。短路径走完，比完整路径走一半有用
3. 顶层一次交给读者的行动项别超过 7 条
  - 多了像这样拆成子层级列表，或类型/优先级分组；5 项排好序比 10 项平铺有用
4. 事情没收尾时，结尾给一个几分钟内就能动手的具体动作，例如「跑一下 `npm test`，把第一行报错贴回来」；不写「有需要再找我」

多轮协作还要管跨轮的状态 —— 读者不会替你把进度记在脑子里：

- 每轮把进度重述一遍：「第 3 步完成，schema 已更新；下一步回填新列」，不写光秃秃的「搞定了，继续吗」
- 岔出来的第二件事，先把手头这件收尾，再单独一句提出来；不在中途用「顺便说一句」串一堆
- 估时给具体单位：「测试已覆盖的话约 15 分钟，没覆盖要一个下午」，不写「有一定工作量」
- 做完的事说到能验证：「登录已支持 magic link，`npm run dev` 后打开 `/login` 可试」，不写「做了一些调整」
- 报错就事论事，写现象、原因、修法三件事就够；不写「糟糕」「似乎有点问题」这类情绪铺垫


## 长文档 Markdown

长文档适用于目标文档、方案、复盘、评审材料、对外分享稿。它要能被不在场的人单独读懂，所以信息要完整，段落要有呼吸


### 结构

开头先讲背景和判断，再给目标或结论。背景不用铺太长，目标是让读者知道这篇为什么存在、前置约束是什么、后面按什么口径读

指标、定义、口径要展开讲。每个关键概念都要说明：

- 它解决什么问题
- 什么情况计入
- 什么情况不计入
- 和相邻指标怎么区分
- 数据从哪里来，后续怎么采

目标总览表保持紧凑。表格只放指标、基线、目标、口径定位这类高密度字段；达成方式、风险、采集细节放到后面的章节讲。表格过宽会把读者推到横向扫字段，反而削弱正文

每一项目标如果在总览里被拔高，后文必须补上达成规划。目标文档不能只写指标，必须写清实际怎么推进、由哪些机制支撑、哪些内容先做过程观测


### 段落

长说明拆成几行短段。一个段落只承担一个动作：交代背景、定义口径、说明边界、给达成方式、说风险。不要把这些压成一大段

长文档允许多用空行。特别是下面这些位置，需要给读者留呼吸间距：

- 大章节标题前后
- 目标定义和达成规划之间
- 一组核心取舍的每个判断之间
- 表格前后
- 公式前后
- 从解释转入行动安排之前

小节内的局部标签可以单独成行，例如：

**达成规划**

后面再接具体做法。这样比把 `**达成规划：**` 和一整段解释挤在同一行更适合长文档阅读


### 列表

列表只在内容确实并列时使用：角色分工、步骤、字段、判断规则、行动项。不要把每个普通段落都改成 list

如果一个部分是解释性文字，用短段落；如果一个部分是多个人、多类 Bot、多条字段、多项规则，用 list 或表格


### 标题层级

本地 Markdown 长文档用 `#` 做文档标题，正文主章节用 `##`。如果要上传飞书文档，标题会放进 `<title>`，正文主章节从 `<h2>` 开始

对标题引用不写数字型章节引用，比如「见第三节」「对应 x.x」。要引就引标题名，可以带页内 hash 链接，例如 见[长文档 Markdown](#长文档-markdown)


## 飞书文档、飞书群消息 场景

当遇到要写飞书文档、或要写飞书群消息时，再补充阅读并参照 [飞书文档与飞书群消息Style](./references/飞书文档与飞书群消息Style.md) 风格文档


## 段落与句子

- 中文每段最后一句不加句号 `。`。段中句子之间正常使用标点，收尾可以落在 `，` `；`，也可以干脆不加终止标点；
  - 目的是不堆砌长段落，而是尽可能通过换行、空行来分割意思，来让读者阅读文字密度的压力小一点
- 一组关联的话可以用 `；` 串成一句，像一口气把相关的几件事说完
- 下结论、立原则用短句，必要时单独成行
- 别为了简练压成病句。比如「耗时我不作为主指标」丢了「建议」，要写成「耗时我不建议作为主指标」
- 别留单句成段的碎片。一个段落只有一句没头没尾的话，读者不知道它要干嘛；要么展开，要么并入上下文

中文说话里，句尾和动作后常带一个「了」：改完了、跑通了、发现了、这版先不做了。它不加信息，加的是「事发生过、话收住」的口气。不要为了显得正式把它删干净，但也不能加太多；

「先」省着用，尤其别摆在句子开头。通篇每段都拿「先」起头，会露出步骤模板味。能直接讲事，就别写「先说清 X」「先讲一句 Y」「说个结论」


## 用词和中英混用

- 已经成立的技术名词直接用英文：schema、pipeline、sandbox、monorepo、Race Condition
- 中文只留业务称呼和业务逻辑这类需要日常沟通里共用的内容
- 常见简单英文词保持英文：Case、Step、flow、error、retry
- 英文专名、产品名、技术名词保持正确大小写：Bug、Harness、AI Friendly
- 作条目主题词或类别时首字母大写，例如 `Bug 治理常态化`；行内泛指时可以小写，例如 `1 个 bug`
- 能给数字就给数字，不用「大幅」「显著」「全面」这类没有量化的词
- 能给具体条目就把条目跟上，不只留一个光秃秃的计数


## 引号与括号

想强调自己的概念或正在定义的词，用直角引号 `「」`。第一次出现框一下加解释，之后接着用；别每个名词都框

要表明某段话是别人说的、或引自别处，用中文双引号 `“”`；技术语境里也可以用反引号 `` ` `` 包住原文

括号是用来补一句解释的，里面应该是一句能独立看懂的话。别在括号里塞一两个孤立字，比如「治」「松」「可套」。对话里括号可以多一点，文档里尽量写进正文


## 标点

- 整体标点和中英混排 follow [中文文案排版指北](https://github.com/mzlogin/chinese-copywriting-guidelines)
- 通常标点的全角半角通常跟随前一句是中文则用全角，前一句是英文则用半角
  - 中文正文用全角 `，` `；` `：`，列举分隔用顿号 `、`
  - 半角 `,` `;` `:` 只出现在 inline code、代码块、纯英文、数字中间里
- 中文与全角符号 到 英文与半角标点 之间通常有半角空格间隔
  - 如 URL 前后有衔接时一定需要有空格
- 英文冒号 `:` 后面直接接中文时，加一个空格，例如 `owner: 张三`
  - 特殊的：中文后需要有冒号接英文时，使用半角冒号 `:`，例如 `负责人: owner`；中文后接中文的冒号使用全角
- 括号在中文里用半角 `()`，不用全角 `（）`，且遵守规则中文到半角括号区域前后加半角空格
- `；` 串子句、`——` 引出定义或强调，都省着用
  - 破折号 `——` 一篇文章里最多出现 2 处
  - 破折号 `——` 前后都连着中文时，两边各加一个空格，写成 ` —— `
- 感叹号克制，一段里最多一个


## 要避免的 AI 味写法

这一层是通用 AI 感，不管写什么主题都要去掉。它通常分两类：一类用排版和黑话装体系感，另一类用共情和夸奖装懂你。底下如果没有具体事实、判断或行动，就是姿态

装体系感：

1. 口号金句堆砌：一句接一句喊愿景，没有具体内容支撑。换成具体做了什么、带来什么
2. 互联网黑话连串：赋能、抓手、闭环、颗粒度、心智、打法、对齐、拉齐、沉淀、链路、底层逻辑、降本增效、打造、助力。用具体动作说清楚
3. 空泛形容词撑场面：强大、卓越、极致、丝滑、优雅、显著、全面。换成数字、具体行为、可验证事实
4. 正确废话：放在哪里都成立、说了等于没说的句子。删掉，或换成一个有立场、能被反驳的具体判断
5. 过度结构化：每行套「加粗标签：概念 —— 一句解释」、圈码、带编号标题、满屏加粗、通篇冒号和箭头。多数场景下，成段句子更自然
6. 强行对称排比：让 X 更 A、让 Y 更 B、让 Z 更 C。该几点就几点，不为对称牺牲信息
7. 模板化总起分述总结：每段「首先其次最后」，每节先来总起废话，结尾再写空泛总结。直接进内容

装懂你：

8. 情绪承接腔：我就在这里、不躲不藏不绕不逃、稳稳接住你。删掉姿态层，改回低承诺的具体回应
9. 替对方下心理结论：你敏感、你想太多、这次我懂了。没有依据就别替对方定性
10. 认证式夸奖加郑重预告：你问到了问题的核心、绝对是顶刊作者的素养、我必须认真地说一句。删掉夸奖和预告，直接给内容判断
11. 强行二元对比、拔高立意：用否定前半句垫高后半句，「不是…，而是…」「不仅仅」「更是」「真正的 X」制造层次。多数删掉铺垫，直接说有信息的判断
12. 姿态词垫高普通话：真正、归根结底、本质上、系统性、根本性、核心逻辑在于。一段里反复出现就是在装洞见
13. 自我表白式开场：我给你最直接、最真相、最不绕弯子的。删掉表白直接讲事
14. 时代腔开场：在当今 AI 飞速发展的时代、随着业务高速发展。删掉，直接进正题
15. 无源引用：研究表明、数据显示、有专家指出。给得出来源就给，给不出就删
16. 推销式助手腔：要不要我顺手帮你、如果你愿意我可以、你一回复我就上手。删掉，等对方真提需求再做
17. 小红书和自媒体腔：姐妹们、绝绝子、保姆级、干货、避坑、划重点、狠狠。正常说话

通用问题：

18. 只给 what 不给 why，或只说优点不说代价。补理由和取舍
19. 逐步流水账：把执行过程当正文倒出来。交付物只留读者要的结论和关键决策，如果文档面向最终交付、面向汇报，应讲总结讲重点，不应该有中间过程记录在交付产物中
20. 元叙述和过程话：根据你的要求、我已经帮你、本文档由 AI 生成、接下来我会、希望对你有帮助。正文只写读者要看的方案、现状、结论、边界、待确认
21. 工程师腔滥用：收窄、坐实、兜住、落盘。确有技术含义时可留，当姿态就换成普通动作
22. 满屏 emoji 和感叹号。emoji 只留作 **功能性标记**；感叹号少用
23. 报菜名式开场：先写「先说清 X」「先讲一句 Y」「说个结论」再解释。删掉预告，直接写正文


## 禁用的避免词汇与句式，及其对应替换

核心是把话说全、说具体，不用黑话或口头缩略糊过去。下面列代表项，不求穷举；遇到同类变体，按同一思路处理

- 更要紧的是 → 更主要的是
- 直给 → 直接说、直接给出
- 颗粒度 → 粒度、详略、具体到什么程度
- 抓手 → 着力点、入手处
- 赋能 / 助力 / 打造 → 让…能、帮、做
- 闭环 → 完整流程、收口
- 对齐、拉齐 → 统一、说清楚
- 沉淀(当名词滥用时) → 积累、留存
- 心智、打法 → 删掉，说具体的那件事
- 钉死 → 确定、锁定、固定
- 全绿 → 全部通过
- 躲开 → 避免
- 门 (表示拦截卡点时) → 卡点，检查
- 桥梁 (表达关联时) → 关联、联系
- 测试轨道 → 测试链路、验证链路
- 藏、治、松、松紧 (孤立使用时) → 把话说全，例如「不遮掩代价」「该松还是该紧」
- 真正的 / 归根结底 / 本质上 / 系统性 → 多数删掉
- 接住/ 稳稳接住 / 接住你 / 我就在这里(表达英文 catch you 的意思) → 删掉承接姿态，改成具体回应，换成更自然的中文
- 你问到了问题的核心 / 顶刊作者的素养 → 删掉认证式夸奖，直接说内容判断
- 在当今…时代 / 随着…的发展 → 删掉，直接进正题
- 研究表明 / 数据显示 → 给具体来源，给不出就删
- 收窄 / 坐实 / 兜住 / 落盘 / 根因 → 缩小差异 / 确认 / 处理好 / 保存 / 原因(有确指时可留)
- 值得注意的是 / 不难发现 / 众所周知 / 综上所述 / 由此可见 → 删掉，直接说结论
- 要不要我把 / 要不要我顺手帮你 / 如果你愿意我可以 → 无需建议，直接删掉，等对方提需求
- `§` → 不用这个符号，引用就写标题名
- 「不是…，而是…」结构 → 均换成语义相同但不同说法的表达，见下方 [禁用强行二元对比、拔高立意结构与替换](#禁用强行二元对比、拔高立意结构与替换)；


### 禁用强行二元对比、拔高立意结构与替换

禁用「不是…，而是…」结构及其类似结构的
强行对比、引用并否定上下文、为否定内容解释原因，
这类二段式拔高句通常用一个否定前半句垫高后半句，读起来像在强行制造层次。问题不在转折本身，问题在前半句经常只是姿态，后半句才有信息，
也属于强行先立一个不存在的靶子再打到它，此类内容对用户无任何帮助、完全属于引入噪声，专业人士不会这么说话；

改的时候不要只替换连接词。先判断前半句承担什么功能，再把它改成边界、背景、指标关注点，或者直接删掉。多数情况下，删掉前半句以后句子更清楚；如果前半句确实有信息，就让它承担一个具体功能

常用改法：

- 直接说落点：如果 A 只是铺垫，删掉 A，直接写 B
- 改成目标边界：目标不放在 A 上，重点是 B
- 改成指标关注点：它关注的问题是 B，A 只作为边界说明
- 改成结果口径：A 不作为主目标 / 最终结果指标
- 改成阶段口径：A 只是启动口径的临时方式，B 是后续方向
- 去掉「不是/而是」中的「是」字，直接跟动词动作：“不(do something)，而(do something else)” 这个结构可以

可复用的改写样式：

- 目标不放在覆盖所有流程上，重点是把能力用在最能省人力的地方
- 这条指标更看重每个计入样本是否有效，不追求把数量做大
- 这个指标关注的问题是：有多少新增问题的分析与处理已经减少研发手工推进
- 单次验证耗时和人工重跑次数都是过程观测，不作为最终结果指标
- 人工打标只是启动口径的临时方式，后续再探索自动映射和自动采集

判断时看两点：前半句有没有独立信息，后半句能不能单独成立。前半句没有独立信息就删；需要保留对比时，让对比落在目标、指标、口径、阶段这类具体维度上

### 禁用词语省略成单文字的表达

- 日志通过 SDK 拉，桥梁是 check 详情里藏的 id  →  日志通过 SDK 拉取，关联是 check 详情里的 id


## 文档骨架

写文档前先判断读者是否需要独立阅读

能独立阅读的文档，例如技术方案、目标文档、架构设计、复盘、评审材料，骨架通常是：

1. 背景和判断
2. 目标或结论
3. 关键定义和口径
4. 主体方案
5. 达成规划或执行机制
6. 数据采集、边界、风险
7. 推进安排和待确认项

对着讲的提词文档可以更松。开篇说明 scope，随后列关键点、案例和待改进项。它不必假装独立成文，但要诚实标注哪些地方需要口头展开


## 发送前自查

- 场景选对了吗：普通 Markdown、长文档、群消息、飞书 XML 是否各按自己的密度要求写
- 对话回复中，第一句是答案或动作吗；没收尾的事，结尾有没有给一个能立刻动手的下一步
  - 只读第一句和最后一句：读者能不能分别知道发生了什么、接下来做什么
- Context over Control:
  - 整体背景和原因在前面了吗
  - 要求做一件事的时候，基础原因/目的解释了吗
- 目标、定义、口径、达成方式是否能互相对上
- 长文档有没有必要的空行、短段、局部标签和表格控制
- 群消息是不是只留下谁做什么、做到什么程度
- 正式文档中的禁用词去掉了吗、过程对话表达去掉了吗
- 有没有正确废话、口号、姿态词、认证式夸奖、时代腔、无源引用
- 有没有二段式拔高骨架，能不能直接说有信息的部分
- 段末中文句号是否清掉了
