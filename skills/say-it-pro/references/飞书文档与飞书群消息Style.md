# 飞书文档与飞书群消息Style

> 飞书文档指飞书云文档 (Lark / Feishu | Docx / Wiki)，对应 CLI 工具与关联 skill 需要 load `lark-doc` skill


## 飞书文档 XML in Markdown

飞书文档 XML 格式适用于最终要上传到飞书 docx/wiki 的私有协议副文本内容；
它的重点是纯 markdown 语法飞书不识别的页面阅读体验的几项 「空段、列表、callout、文字颜色/背景色」 需要用 XML in Markdown 来实现

> 纯 XML 也是一个合法的 Markdown 语法文件，因此均优先使用 markdown 语法作为内容载体，仅在必要时增加 inline XML 给飞书文档


### 上传与 title

- 本地 md 用 `lark-cli docs +create --doc-format markdown` 直传，不需要整篇转纯 XML
- 全文仅应该有一个 `<title>`，或 `H1`
  - 首行 `# 标题` 只在全文唯一 H1 时才被提升为文档标题；正文还有其他 `#` 章节时不提升，title 会变 Untitled。通用安全式(本地 md 保持完整、零中间文件)：
  `lark-cli docs +create --doc-format markdown --title "$(head -1 f.md | sed 's/^# //')" --content "$(tail -n +2 f.md)"`
- 非标题的正文主章节用 `##`(对应飞书 H2)，子节用 `###`，不必在正文重复一个标题行


### XML in Markdown 白名单与黑名单

以下均为真实上传回读验证过的结论。内嵌在 md 里**有效**的 XML：

- `<callout emoji=".." background-color=".." border-color="..">` 高亮块，背景/边框色也保留；内部段落要用 `<p>`，内部加粗要用 `<b>`(`**` 在 XML 块内不解析)
- `<p></p>` 空段，用于留白
- `<cite type="user" user-id="ou_..">` @人(服务端解析成真实 mention)
- `<p>句一<br/>句二</p>` 段内换行
- `<table>` + `<colgroup>` 控列宽 —— 这是唯一 md 表达不了、必要时整篇改写 XML 的理由
- LaTeX 公式直接写 md 惯用的 `$...$` 行内、`$$...$$` 块级，导入即真实公式渲染(自动转 `<latex>`)；多行 `$$` 块变成独占一段的公式，视觉上就是块级，`<latex>` 标签也有效但没必要

写了**无效**、还会脏页面的：

- `> [!info]` `[!NOTE]` 等 GFM alert：不转 callout，`[!info]` 留成引用块里的字面文本
- 独立成行的裸 `<br/>`：被直接吞掉(`<br/>` 只能在 `<p>` 等容器内部用)
- `&nbsp;`：变成字面文本脏段
- ` ```math ` 代码块：保持代码块，不渲染公式

通用飞书文档 XML 规则细节需要额外 load `lark-doc` skill 并阅读其中 xml 说明


### 换行与空行

飞书 md 导入的换行**偏离 CommonMark**，按「一行就是一行」理解：

- 单个换行 = 同一 block 内换行(不是标准 md 的空格合并)；行尾双空格、行尾 `\` 与之等价，不用特意写
- 空行 = 分段(新 block)；连续多个空行折叠成一个，堆空行做不出更大间距
- 需要比段间距更大的留白用 `<p></p>`，尤其主章节前、表格后、公式前后、核心判断之间
- 两种换行是不同的东西：独立 block 有段间距、可单独选中和评论，段内换行只是折行。需要显式控制时 `<p>a</p><p>b</p>` vs `<p>a<br/>b</p>`
- 飞书文档任何一级 Header (H1 H2 H3 H4 ...) 前如果有上一节内容，则从上一节内容到下一节 Header 之间必须有一视觉空行来体现呼吸间距 `<p></p>`
  - Header 之后的空行则可有可无 (因为页面上默认样式 margin 足够)


### 局部标签

长飞书文档里，重要局部标签优先单独成段：

```markdown
**达成规划**
需求侧按自然推进，不额外制造需求...
```

短标签加解释挤在同一段会显得密，尤其在飞书里更明显。只有定义项很短、读者一眼能扫完时，才写成：

```markdown
**单次修改验证耗时**：目标表里的观测值是从半小时降到 15min...
```


### 列表与表格

角色分工、Bot 职责、字段枚举、档位规则适合列表或表格。解释性段落继续用短段落，不要为了显得结构化把它们全改成 list

指标总览表要窄。过宽的表格在飞书里阅读成本高，目标、口径、基线这些放表里；达成抓手和执行规划放后文


### 立场要求

所有飞书文档内容，默认内容立场都是「由作为文档所有者、谈论事项的负责人、跟你对话的用户 的我本人对外给别人讲解、汇报用的文档」，
也就是其内容只跟作为 文档的所有者、谈论事项的负责人、跟你对话的用户 的我本人的主体与对应人类读者的主体有关，一共只有两方主体；
内容里不应该出现作为 Agent 的你的主体，因此不能出现作为你的主体写给作为用户的我的话写到了这个文档中，不要作为 Agent 的你与用户我的协作过程、修改过程、响应用户要求的过程，也不要写文档编排过程；
飞书文档不是你跟我两个主体的对话，而是事项负责人我跟人类读者的对话，文档只应该写读者需要看到的方案、现状、结论、边界和待确认项；


### 特殊富文本内容要求

- 提到的任何人名称呼一类的，如果用户没有特别指定要求，都应该默认通过 lark-contact 搜索到实际员工个体在文档中 @人 (使用 `<cite>`)
  - 并且通常这个人应该在部门、文档、群中与我有关联，以防止因为语音 typo、重名而 metion 到无关人员
- 如果被关联文档是飞书文档，应该直接放飞书文档 url 并不用再加 Markdown Link 格式链接，目标是需要飞书文档 url 会在飞书文档内被解析成实时文档 title，能在源文档改名时获得在被关联文档中自动被重命名的能力
  - 不是飞书文档的其他链接需要使用 Markdown Link 格式链接来显示 Title
- When create or modify Lark/Feishu docs with local markdown file which has linked some images, MUST ensure those images should upload to Lark/Feishu Docs

### 上传前检查

- 公式是否都写成 `$...$` / `$$...$$`，没有落进 ` ```math ` 或普通代码块
- 需要留白的位置是否有 `<p></p>`；没有靠堆连续空行、裸 `<br/>`、`&nbsp;` 做间距
- callout 是否用 `<callout>` 而不是 `> [!info]`；其内部加粗是否用 `<b>`
- 人名是否都用 `<cite type="user">` @ 到人
- 是否有 `<title>` 或 全文唯一 H1，首行标题与 `--title` 的关系是否处理(全文唯一 H1 才会自动提升)
- 合理的 `<H2>`、必要的 `<p></p>` 空行、真实 `<ul><li>`、可渲染的 `<latex>`
- 是否把真实并列项写成列表、多维口径写成表格
- 是否存在过宽表格、满屏加粗、每段一个标签的模板感
- 群消息承载文档是否仍然保持群消息密度


## 飞书群消息格式要点

群消息是对话里最总结性的一种：收件人多半在场或知情，目标是同步结论、派活、拉进度。语气短、信息密，是管理者随手敲的一张工作便条

群消息的信息量和长文档不同。不要复述会议脉络、争论过程、完整论证；只留定了什么、谁做、做到什么程度

- 开头顶多一句说明来源，立刻进条目
- 顶层条目都应该是有人要做的事
- 最要紧的活排最前：收件人只扫前两三段，也该拿到自己那份重点
- 顶层一次交给读者的行动项别超过 7 条
  - 多了像这样拆成子层级列表，或类型/优先级分组；5 项排好序比 10 项平铺有用
- 一行一个 workstream，用 `- 主题: 动作 @负责人`
- 主题标签用普通文本，不加粗
- 每行只把关键动作或诉求加粗一处，方便负责人扫到自己要做什么
- `@` 到人，自己的活也 `@` 自己名字，不写「我」
- 牵出的 ticket、单号、文档链接挂成子项
- 群消息不使用 H1 / H2 / H3，最多用 bold

啰嗦写法：

> 历史数据是 6 月存量一千来个 Bug 里只有 1 个是研发用新流程完整跑通的，覆盖太低，所以我们转成常态化，具体是有 Bug 分的同学每人每周跟一个

总结写法：

> Bug 治理常态化: 有 Bug 的同学 **每人每周跟进 1 个 Bug 跑新流程** @负责人

飞书群消息如果通过飞书文档承载，内容密度仍按群消息格式要求
