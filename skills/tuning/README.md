# tuning

Code review 批注的批量执行器。Review Agent 产出的代码时，直接在代码里留下 `/// fix:` `/// refactor:` `/// ??:` 格式的行内批注，然后运行 `/tuning`，Agent 会扫描全部批注、读懂上下文、列出执行计划，确认后逐条修改并验证

比起在聊天框里逐条描述「第 42 行改一下、那个函数抽出去」，批注直接写在代码位置上，指代零歧义，还能一次攒一批集中处理

## 安装

```bash
npx skills add zthxxx/zthxxx-skills --skill tuning
```

## 怎么用

1. Review 代码时在需要修改的位置留下批注 (任何语言的注释语法都可以)：

```typescript
/// fix: handle null case here

/// refactor: extract this into a shared utility

/// ??: why was the timeout increased to 30s?
```

2. 在 Claude Code 里运行 `/tuning`

3. Agent 展示 checkpoint 列表，确认后开始执行；有歧义或批注互相冲突时会先停下来问清楚

三种批注的行为：

| 批注 | 含义 | Agent 的动作 |
|------|------|-------------|
| `/// fix:` | 要修的问题 | 按描述修复；说「回退到旧版」时会从 git 历史取回旧代码，不凭记忆重写 |
| `/// refactor:` | 要做的结构调整 | 找到所有受影响的调用点一起改，不只改标记处那一个 |
| `/// ??:` | 「这里为什么这么改」 | 从 git 历史查明原因，写成解释 why 的代码注释留在原地 |

## 有什么效果

- 整个流程走固定的 7 个阶段：项目上下文 → 发现批注 → 通读上下文 → 交叉分析与计划 → 逐条执行 → lint/测试验证 → 复查后清理批注标记
- 批注是成组处理的：不同文件里指向同一问题的批注会被识别为关联项，一起规划、一起改，避免各改各的导致不一致
- 批注里带的领域知识 (坑、设计取舍、为什么这么做) 不会随标记一起删掉，会保留成代码注释或写进 spec
- 只有验证通过、确认改对了的批注标记才会被移除；没改完的留在原地并说明原因
